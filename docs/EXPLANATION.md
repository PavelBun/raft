# Объяснение реализации для защиты

## 1. Что именно сделано

Это первый этап Raft: каждый процесс представляет один узел. Узел умеет
участвовать в выборах, стать лидером, поддерживать лидерство heartbeat-сообщениями
и показывать своё состояние через HTTP. Клиентских записей, журнала и базы
key-value ещё нет. Поэтому корректнее называть проект реализацией подсистемы
выборов Raft, а не готовым алгоритмом репликации или готовой распределённой БД.

Основой служит [оригинальная статья Raft](https://raft.github.io/raft.pdf),
раздел 5.2 и схема правил на Figure 2. Названия RPC соответствуют Raft, но
`AppendEntries` на этом этапе передаёт только heartbeat.

## 2. Связь со слайдами

На слайдах выборы описаны через абстракцию детектора отказов и выбор процесса
с максимальным рангом среди неподозреваемых. В этом проекте нет ни множества
`suspected`, ни выбора максимального ID: используется механизм Raft — сроки,
таймауты и голосование большинством.

Связь есть на уровне задачи: узлам необходимо согласовать координатора, а
отсутствие сообщений заставляет подозревать проблему с действующим лидером.
Таймаут не позволяет отличить остановку процесса от задержки или разрыва сети.
Следовательно, heartbeat с таймаутом нельзя назвать perfect failure detector.

Для практического прогресса предполагается, что достаточно долго существует
взаимно доступное большинство и задержки достаточно малы относительно таймаутов.
При неограниченных задержках завершение выборов не гарантируется. Безопасность
голосования обеспечивается сроками и правилом одного голоса, а не точностью часов.

Узлы рассматриваются как не византийские: они могут остановиться или потерять
связь, но не подделывают сообщения и не нарушают алгоритм намеренно. Обычный
перезапуск поддерживается сохранением срока и голоса на диск. Это добавляет
элемент crash-recovery, но не реализует всю абстракцию fail-recovery со слайда:
например, отдельного протокола stubborn links здесь нет.

## 3. Устройство проекта

```text
cmd/raft/main.go           — параметры запуска, сборка узла, жизненный цикл
internal/raft/node.go      — типы, поля Node, New, общие помощники, Status
internal/raft/loop.go      — Run и handleTick: тикер и решение «что делать сейчас»
internal/raft/election.go  — выборы: HandleVote, startElection, requestVote
internal/raft/heartbeat.go — heartbeat: HandleHeartbeat, sendHeartbeat
internal/raft/http.go      — HTTP-клиент и HTTP API
internal/raft/storage.go   — сохранение срока и голоса
internal/raft/node_test.go — модульные и интеграционные тесты
```

`cmd` содержит запускаемую программу. `internal` содержит внутренний пакет:
Go не позволяет импортировать его из произвольных внешних проектов.
`go.mod` задаёт имя модуля `raft-study`, поэтому импорт имеет вид
`raft-study/internal/raft`.

Разделение полезно для следующих этапов: правила работы с журналом добавятся
к ядру, HTTP останется транспортом, а хранение можно будет расширить журналом.

## 4. Состояния и поля Node

В `node.go` тип `Role` — строка с тремя константами:

| Роль | Поведение |
|---|---|
| `follower` | Принимает heartbeat и голосует; при истечении таймаута начинает выборы |
| `candidate` | Голосует за себя и запрашивает голоса остальных |
| `leader` | Регулярно отправляет heartbeat |

Основные поля `Node`:

| Поле | Что означает |
|---|---|
| `cfg` | ID, адреса остальных узлов и интервалы |
| `state.Term` | Текущий срок, логический номер эпохи |
| `state.VotedFor` | Кому отдан голос в текущем сроке |
| `role` | Локальная роль |
| `leaderID` | Лидер, известный этому узлу |
| `votes` | Голоса собственной текущей кампании |
| `deadline` | Когда начать новые выборы при отсутствии heartbeat |
| `nextHeartbeat` | Когда лидеру отправить следующую порцию heartbeat |
| `failure` | Необратимая для этого экземпляра ошибка хранения |
| `mu` | Mutex для защиты состояния |

Срок — не время в секундах. Например, после неудачных выборов срок может стать
2, затем 3. Некоторые сроки могут закончиться без лидера.

`leaderID` не сохраняется на диск: после перезапуска узел сначала не знает
действующего лидера. Он узнает его из heartbeat. Сохраняются только `Term`
и `VotedFor`, необходимые для соблюдения правил голосования.

## 5. Создание узла: New

`New` проверяет обязательные зависимости и параметры времени. В этом проекте
должно выполняться `0 < 2 * heartbeat < election-min < election-max`.
Это удобная проверка для учебного запуска, а не математическая гарантия:
пауза планировщика или медленный диск всё равно могут вызвать новые выборы.

Адресная таблица копируется. В ней содержатся только другие узлы, поэтому
полный размер кластера равен `len(Peers) + 1`. Затем загружается сохранённое
состояние, устанавливается роль follower и выбирается случайный таймаут.
Если файл отсутствует, узел начинает со срока 0 и без голоса; если файл повреждён,
запуск завершается с ошибкой, а не молча обнуляет состояние.

## 6. Как выбирается лидер

Для трёх узлов большинство вычисляется так:

```go
(len(n.cfg.Peers)+1)/2 + 1
```

Здесь два peers плюс сам узел дают три участника. Целочисленное деление
`3 / 2` даёт 1, затем добавляется 1: необходимо два голоса.
Для пяти узлов нужно три голоса; для одного достаточно собственного голоса.
Недоступные узлы остаются в составе кластера и в знаменателе большинства.

Допустим, n2 первым дождался таймаута. `Run` передаёт тик в `handleTick`,
тот проверяет таймаут и вызывает `startElectionLocked`. Этот метод:

1. Увеличивает текущий срок.
2. Записывает свой ID в `VotedFor`.
3. Становится candidate и устанавливает `votes = 1`.
4. Выбирает новый таймаут на случай неудачи.
5. Сохраняет срок и голос **до отправки запросов**.

После этого `handleTick` освобождает mutex и вызывает `broadcastVoteRequests`:
для каждого peer запускается goroutine с `RequestVote`. Сеть не удерживает mutex.

Если один из остальных узлов даёт голос, число голосов становится 2.
`becomeLeaderLocked` меняет роль на leader, устанавливает собственный `leaderID`
и делает время следующего heartbeat нулевым. Поэтому heartbeat отправится
на ближайшем тике цикла, без ожидания полного интервала.

Если большинство не собрано, узел остаётся candidate. После следующего таймаута
он увеличивает срок и повторяет выборы. Это также решает ситуацию разделённых
голосов, когда несколько кандидатов одновременно проголосовали за себя.

Таймаут выбирается в диапазоне `[600ms, 1200ms)` по умолчанию. Случайность
нужна, чтобы узлы с меньшей вероятностью начинали выборы одновременно и снова
делили голоса. ID узла при выборе победителя не сравнивается.

## 7. Обработка запроса голоса: HandleVote

Функция берёт mutex, проверяет наличие ошибки хранения и принадлежность
кандидата кластеру. Затем вызывает `observeTermLocked`.

Если входящий срок больше текущего, узел становится follower, принимает новый
срок и очищает голос **старого срока**. Новое состояние сохраняется на диск.
Если входящий срок меньше текущего, возвращается отказ с актуальным сроком.

При равных сроках голос даётся, если `VotedFor` пуст или уже равен тому же
кандидату. Повторный запрос от того же кандидата допустим: это идемпотентность.
Запрос от другого кандидата в том же сроке отклоняется.

Перед положительным ответом голос сохраняется, затем сбрасывается таймаут
выборов. Отказ в голосе при равном сроке не сбрасывает таймаут. При переходе
в новый срок таймаут в этой реализации переустанавливается самим
`observeTermLocked`.

В полном Raft нужно также проверить актуальность журнала кандидата.
Здесь журналов нет, все они условно пусты, поэтому проверка ещё не нужна.
Когда появится репликация, в запрос добавятся `last_log_index`, `last_log_term`
и соответствующее условие выдачи голоса. Просто добавить записи в нынешнюю
версию без этой проверки нельзя.

## 8. Ответы на запросы голосов: requestVote

HTTP-вызов выполняется без mutex. Ошибка сети означает отсутствие голоса,
а не голос против и не доказательство смерти процесса.

После ответа снова берётся mutex. Более высокий срок из ответа всегда
заставляет перейти в follower. Затем проверяется, что узел ещё candidate,
его текущий срок совпадает со сроком отправленного запроса и ответ относится
к тому же сроку.

Это защита от запоздалых ответов: если запрос был отправлен в сроке 2, а узел
уже перешёл в срок 3, старый положительный ответ нельзя считать в новых выборах.

На каждого peer отправляется один запрос на кампанию; ответ учитывается один
раз. После достижения большинства роль уже leader, поэтому дальнейшие ответы
не увеличивают счётчик. Для этой схемы отдельное множество проголосовавших ID
не требуется; при добавлении повторных запросов понадобится защита от повторного
подсчёта голосов.

## 9. Heartbeat: HandleHeartbeat и sendHeartbeat

Лидер каждые 100 ms отправляет всем остальным сообщение со своим сроком и ID.
Маршрут называется `/raft/append-entries`, потому что в полном Raft пустой
`AppendEntries` служит heartbeat. Здесь это сокращённый собственный формат,
он не совместим по сети с произвольной сторонней реализацией Raft.

Получатель отклоняет сообщение с меньшим сроком. Сообщение с равным или большим
сроком переводит его в follower, обновляет известного лидера и сбрасывает
таймаут выборов. При равном сроке уже отданный голос сохраняется: сбросить его
нельзя, иначе можно проголосовать дважды. При большем сроке очищается старый голос.

Если кандидат получает heartbeat лидера своего срока, он прекращает свою
кампанию и становится follower. Если лидер видит в ответе больший срок, он
также становится follower. Ошибка сети сама по себе не меняет роль лидера.

## 10. Почему два лидера не могут быть избраны в одном сроке

Для избрания каждому кандидату нужно строгое большинство фиксированного
кластера. Любые два таких большинства пересекаются хотя бы в одном узле.
Если бы два кандидата были избраны в одном сроке, узел из пересечения должен
был бы проголосовать за обоих. Это запрещено правилом `VotedFor` и сохранением
голоса между перезапусками.

Утверждение относится к **одному сроку**. При разделении сети старый лидер
может продолжать локально считать себя лидером в сроке 5, пока большинство
избирает нового в сроке 6. Это не два избранных лидера одного срока.
`GET /status` показывает локальное мнение и не доказывает текущую связь с
большинством. В этой версии нет check-quorum и нет клиентских операций.
При дальнейшем добавлении записи и чтения нужны соответствующие правила
Raft для подтверждения операций, а не одна проверка `role == leader`.

## 11. Параллельность в Go

`go func(...)` запускает goroutine: лёгкую задачу, которой управляет runtime Go.
Запросы к peers идут параллельно, чтобы один медленный сервер не задерживал
обращения к остальным.

HTTP-сервер также обрабатывает запросы конкурентно. Одновременно могут работать
таймер выборов, входящий запрос голоса, heartbeat и `/status`. Поэтому изменяемые
поля защищены `sync.Mutex`. Без него возможна не только гонка данных, но и
ошибка протокола: два обработчика могут одновременно увидеть пустой `VotedFor`
и выдать голоса разным кандидатам.

Суффикс `Locked` означает: вызывающая функция уже должна держать mutex.
Дисковая запись остаётся под mutex, чтобы никто не подтвердил голос до его
сохранения. Для учебного проекта это просто; для высокой нагрузки понадобится
более сложная организация хранения.

Сетевой запрос выполняется **после освобождения mutex**. Затем состояние
проверяется заново: за время ожидания роль или срок могли измениться.
`Status` возвращает копию адресной таблицы, чтобы вызывающий код не получил
доступ к внутренней изменяемой структуре.

`time.Ticker` — периодический источник событий. Пример:

```go
ticker := time.NewTicker(10 * time.Millisecond)
defer ticker.Stop()
```

Примерно каждые 10 ms тикер передаёт время в канал `ticker.C`. Основной цикл
ждёт либо это событие, либо отмену через `ctx.Done()`. В ожидании событий
не происходит непрерывного опроса, который тратил бы процессор впустую.
При медленной обработке тики могут пропускаться: это не жёсткие часы реального времени.

Тик — повод проверить таймеры, а не команда немедленно проводить выборы.
Например, при таймауте выборов 800 ms тики на 10, 20 и 30 ms сами по себе
ничего не меняют. Выборы начнутся, когда проверка обнаружит истёкший `deadline`,
если до этого актуальный heartbeat не перенесёт его. Heartbeat отправляется
по собственному расписанию, по умолчанию раз в 100 ms.

Основной цикл оставлен коротким, а действия распределены по методам:

| Метод | Ответственность |
|---|---|
| `Run` | Ждать тик или отмену; при остановке дождаться исходящих задач |
| `handleTick` | Проверить состояние и решить, пора ли начать выборы или отправить heartbeat |
| `startElectionLocked` | Подготовить и сохранить новую кампанию под mutex |
| `broadcastVoteRequests` | Запустить отдельный запрос голоса каждому peer |
| `broadcastHeartbeats` | Запустить отдельный heartbeat каждому peer |
| `requestVote` | Получить ответ одного peer и учесть голос, если кампания ещё актуальна |
| `sendHeartbeat` | Получить ответ одного peer и уступить при обнаружении большего срока |

`context.Context` передаёт отмену запросам при остановке.
`sync.WaitGroup` позволяет дождаться завершения исходящих goroutine.
Задачи добавляются из методов рассылки, вызванных основным циклом. При выходе
цикл прекращает их добавление, отменяет контекст и ждёт оставшиеся задачи.
Это ожидание завершения при остановке, а не ожидание всех голосов в каждом раунде.

## 12. HTTP и REST

`HTTPTransport.call` сериализует структуру в JSON, создаёт POST-запрос,
отправляет его через `http.Client` и декодирует ответ. JSON-теги вроде
`json:"candidate_id"` задают имена полей в сети. Клиент ограничивает время RPC,
а контекст позволяет отменить его раньше.

`Handler` создаёт `http.ServeMux`. Шаблоны `GET /status` и
`POST /raft/request-vote` одновременно задают путь и разрешённый метод.
Входящий JSON ограничен 64 KiB, неизвестные поля и лишний JSON после первого
объекта отвергаются. Внутренние маршруты — это RPC поверх HTTP/JSON;
`GET /status` — пользовательский REST endpoint чтения состояния.

## 13. Сохранение состояния

`Storage` — интерфейс с `Load` и `Save`. Ядро зависит от поведения хранилища,
а не от конкретного файла. В тестах можно использовать память или искусственную
ошибку диска; в приложении используется `FileStorage`.

`state.json` содержит примерно следующее:

```json
{"term":3,"voted_for":"n2"}
```

`Save` создаёт временный файл в том же каталоге, пишет JSON, вызывает `Sync`,
закрывает файл и переименовывает его в `state.json`. Это уменьшает риск получить
частично записанный JSON и поддерживает обычные остановки и перезапуски процесса.
Переименование и устойчивость при отключении питания зависят от ОС и файловой
системы; здесь нет полноценного промышленного transactional storage и синхронизации
каталога. Особенно на Windows нельзя обещать универсальную атомарность `Rename`.

Если запись не удалась, узел не подтверждает голос и прекращает участие.
Продолжать голосование после ошибки было бы опасно: при перезапуске узел мог
забыть уже выданный голос. Данные нельзя удалять между перезапусками в том же
кластере и нельзя делить каталог между процессами.

## 14. Точка входа и остановка

`main.go` разбирает флаги через пакет `flag`. `parsePeers` проверяет формат
`id=http://host:port`, запрещает собственный ID и дубли peers. Далее создаются
клиент, хранилище и узел.

Сначала выполняется `net.Listen`, и только затем запускаются сервер и `Run`.
Если порт занят, процесс завершится до начала выборов. Это исключает ситуацию,
когда недоступный по своему порту процесс уже объявляет себя лидером.

Сервер и цикл узла отправляют результат в канал `results`. При Ctrl+C,
ошибке сервера или ошибке ядра отменяется контекст, HTTP-сервер корректно
останавливается и программа ждёт завершения обеих частей. Отдельный контекст
для shutdown имеет срок 3 секунды; при превышении сервер закрывается принудительно.

## 15. Что проверяют тесты

Тесты проверяют конкретные свойства, а не только успешную сборку:

- Один голос на срок, включая повторный запуск с тем же файлом состояния.
- Повторный голос за того же кандидата и возможность голосовать в новом сроке.
- Конкурентные запросы двух кандидатов: голоса получает только один ID.
- Отказ старым сообщениям и переход в follower при актуальном heartbeat.
- Сохранение голоса при heartbeat того же срока.
- Прекращение участия после ошибки хранилища.
- Запоздалые ответы и больший срок из ответа RPC.
- HTTP-обмен, отказ неизвестному участнику, некорректный метод и пустой JSON.
- Повторные выборы без ответов peers.
- Выбор единственного лидера и стабильность срока при heartbeat через настоящие HTTP-серверы.
- Перевыборы после остановки лидера; невозможность избрания оставшегося follower без большинства.
- Самоизбрание кластера из одного узла.

Интеграционные тесты запускают реальные локальные HTTP-серверы в одном процессе.
Это проверяет таймеры и транспорт, но не является формальным доказательством
корректности и не заменяет испытания всех возможных сетевых разделений.

## 16. Короткий рассказ на защите

«Я реализовал первый этап — выборы лидера Raft и API статуса. Каждый узел
запускается отдельным Go-процессом и имеет роли follower, candidate и leader.
При отсутствии heartbeat узел ждёт случайный таймаут, увеличивает срок,
голосует за себя и запрашивает голоса остальных. Для победы нужно строгое
большинство фиксированного состава кластера. В одном сроке каждый узел голосует
только за одного кандидата; срок и голос сохраняются на диск. Лидер отправляет
heartbeat, а обнаружение большего срока переводит узел обратно в follower.
REST endpoint `/status` показывает локальную роль, срок и известного лидера.
Журнал пока отсутствует: его репликация и проверка актуальности журнала при
голосовании будут добавлены на следующем этапе».

## 17. Частые вопросы

**Почему нельзя просто выбрать максимальный ID?** Это был бы другой алгоритм,
близкий к слайдам. Задание развивается в Raft, где согласование лидерства
осуществляется большинством голосов в сроке.

**Почему нужны случайные таймауты?** Чтобы уменьшить вероятность одновременного
начала кампаний и повторного разделения голосов.

**Почему срок хранится на диске?** Чтобы после перезапуска не принимать
устаревшие сообщения как новые. Голос хранится, чтобы не голосовать повторно
за другого кандидата в том же сроке.

**Почему после остановки двух серверов кластер не уменьшается до одного?**
Состав кластера фиксирован. Автоматически считать недоступных исключёнными
опасно: две части сети могли бы каждая назначить себе большинство.

**Гарантируется ли выбор лидера при любой сети?** Нет. Без доступного большинства
или при постоянных больших задержках прогресс не гарантируется.

**Почему старый лидер при изоляции не всегда становится follower?** В базовых
правилах он уступает при обнаружении большего срока. В этой версии нет
дополнительного check-quorum, который заставлял бы уступать при длительной
потере связи с большинством. Статус отражает локальное состояние.

**Что нужно добавить на этапе 2?** Записи журнала и их хранение, поля
`prev_log_index`, `prev_log_term`, `entries`, `leader_commit` в AppendEntries,
проверку актуальности журнала кандидата, `nextIndex`/`matchIndex` лидера,
правила подтверждения и применения записей, клиентское добавление и просмотр
журнала. Нынешний heartbeat — только основа для этого расширения.
