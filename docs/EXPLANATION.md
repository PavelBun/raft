# Объяснение реализации для защиты

## 1. Что именно сделано

Это первые два этапа Raft. Этап 1: каркас узла, выборы лидера и API статуса.
Этап 2: репликация журнала и API для добавления записей и просмотра журнала.
Каждый процесс представляет один узел. Машины состояний (key-value) пока нет:
зафиксированные записи только помечаются применёнными и пишутся в лог процесса.

Основой служит [оригинальная статья Raft](https://raft.github.io/raft.pdf):
разделы 5.1–5.4 и схема правил на Figure 2. Имена полей RPC и правила
соответствуют Figure 2. Сознательно не сделано то, чего на Figure 2 нет:
пустая запись нового лидера (§8), снимки журнала (§7), смена состава кластера (§6),
ускоренный откат `nextIndex` и check-quorum.

## 2. Связь со слайдами

На слайдах выборы описаны через абстракцию детектора отказов и выбор процесса
с максимальным рангом среди неподозреваемых. В этом проекте нет ни множества
`suspected`, ни выбора максимального ID: используется механизм Raft — сроки,
таймауты и голосование большинством.

Связь есть на уровне задачи: узлам необходимо согласовать координатора, а
отсутствие сообщений заставляет подозревать проблему с действующим лидером.
Таймаут не позволяет отличить остановку процесса от задержки или разрыва сети.
Следовательно, heartbeat с таймаутом нельзя назвать perfect failure detector.

Для практического прогресса предполагается, что достаточно долго существует
взаимно доступное большинство и задержки достаточно малы относительно таймаутов.
При неограниченных задержках завершение выборов не гарантируется. Безопасность
голосования обеспечивается сроками и правилом одного голоса, а не точностью часов.

Узлы рассматриваются как не византийские: они могут остановиться или потерять
связь, но не подделывают сообщения и не нарушают алгоритм намеренно. Обычный
перезапуск поддерживается сохранением срока и голоса на диск. Это добавляет
элемент crash-recovery, но не реализует всю абстракцию fail-recovery со слайда:
например, отдельного протокола stubborn links здесь нет.

## 3. Устройство проекта

```text
cmd/raft/main.go           — параметры запуска, сборка узла, жизненный цикл
internal/raft/node.go      — типы, поля Node, New, общие помощники, Status
internal/raft/loop.go      — Run и handleTick: тикер и решение «что делать сейчас»
internal/raft/election.go  — выборы: HandleVote, startElection, requestVote
internal/raft/replication.go — HandleAppendEntries, replicateTo, фиксация записей
internal/raft/client.go    — запросы клиента: Propose, WaitCommitted, Log
internal/raft/http.go      — HTTP-клиент и HTTP API
internal/raft/storage.go   — сохранение срока, голоса и журнала
internal/raft/node_test.go, replication_test.go — модульные и интеграционные тесты
```

`cmd` содержит запускаемую программу. `internal` содержит внутренний пакет:
Go не позволяет импортировать его из произвольных внешних проектов.
`go.mod` задаёт имя модуля `raft-study`, поэтому импорт имеет вид
`raft-study/internal/raft`.

Разделение полезно для следующих этапов: машина состояний подключится к
`applyCommittedLocked`, а правила Raft и HTTP-транспорт при этом не изменятся.

## 4. Состояния и поля Node

В `node.go` тип `Role` — строка с тремя константами:

| Роль | Поведение |
|---|---|
| `follower` | Принимает AppendEntries и голосует; при истечении таймаута начинает выборы |
| `candidate` | Голосует за себя и запрашивает голоса остальных |
| `leader` | Принимает команды клиентов и реплицирует журнал через AppendEntries |

Основные поля `Node`:

| Поле | Что означает |
|---|---|
| `cfg` | ID, адреса остальных узлов и интервалы |
| `state.Term` | Текущий срок, логический номер эпохи |
| `state.VotedFor` | Кому отдан голос в текущем сроке |
| `state.Log` | Журнал: записи с индексом, сроком и командой |
| `commitIndex` | Наибольший индекс, про который известно, что он зафиксирован |
| `lastApplied` | Наибольший индекс, применённый к машине состояний |
| `nextIndex[peer]` | Только у лидера: какую запись отправить этому peer следующей |
| `matchIndex[peer]` | Только у лидера: до какого индекса журнал peer точно совпадает |
| `changed` | Канал, который будит клиентов, ждущих фиксации записи |
| `role` | Локальная роль |
| `leaderID` | Лидер, известный этому узлу |
| `votes` | Голоса собственной текущей кампании |
| `deadline` | Когда начать новые выборы при отсутствии heartbeat |
| `nextHeartbeat` | Когда лидеру отправить следующую порцию heartbeat |
| `failure` | Необратимая для этого экземпляра ошибка хранения |
| `mu` | Mutex для защиты состояния |

Срок — не время в секундах. Например, после неудачных выборов срок может стать
2, затем 3. Некоторые сроки могут закончиться без лидера.

`leaderID` не сохраняется на диск: после перезапуска узел сначала не знает
действующего лидера. Он узнает его из heartbeat. Сохраняются только `Term`,
`VotedFor` и `Log`, как в Figure 2. `commitIndex` и `lastApplied` начинаются
с нуля после перезапуска: узел заново узнаёт их от лидера.

## 5. Создание узла: New

`New` проверяет обязательные зависимости и параметры времени. В этом проекте
должно выполняться `0 < 2 * heartbeat < election-min < election-max`.
Это удобная проверка для учебного запуска, а не математическая гарантия:
пауза планировщика или медленный диск всё равно могут вызвать новые выборы.

Адресная таблица копируется. В ней содержатся только другие узлы, поэтому
полный размер кластера равен `len(Peers) + 1`. Затем загружается сохранённое
состояние, устанавливается роль follower и выбирается случайный таймаут.
Если файл отсутствует, узел начинает со срока 0, без голоса и с пустым журналом.
Если файл повреждён или журнал в нём некорректен, запуск завершается с ошибкой,
а не молча обнуляет состояние.

## 6. Как выбирается лидер

Для трёх узлов большинство вычисляется так:

```go
(len(n.cfg.Peers)+1)/2 + 1
```

Здесь два peers плюс сам узел дают три участника. Целочисленное деление
`3 / 2` даёт 1, затем добавляется 1: необходимо два голоса.
Для пяти узлов нужно три голоса; для одного достаточно собственного голоса.
Недоступные узлы остаются в составе кластера и в знаменателе большинства.

Допустим, n2 первым дождался таймаута. `Run` передаёт тик в `handleTick`,
тот проверяет таймаут и вызывает `startElectionLocked`. Этот метод:

1. Увеличивает текущий срок.
2. Записывает свой ID в `VotedFor`.
3. Становится candidate и устанавливает `votes = 1`.
4. Выбирает новый таймаут на случай неудачи.
5. Сохраняет срок и голос **до отправки запросов**.

После этого `handleTick` освобождает mutex и вызывает `broadcastVoteRequests`:
для каждого peer запускается goroutine с `RequestVote`. Сеть не удерживает mutex.

Если один из остальных узлов даёт голос, число голосов становится 2.
`becomeLeaderLocked` меняет роль на leader, устанавливает собственный `leaderID`,
заполняет `nextIndex` (последний индекс + 1) и `matchIndex` (0) для каждого peer
и делает время следующего heartbeat нулевым. Поэтому AppendEntries отправится
на ближайшем тике цикла, без ожидания полного интервала.

Если большинство не собрано, узел остаётся candidate. После следующего таймаута
он увеличивает срок и повторяет выборы. Это также решает ситуацию разделённых
голосов, когда несколько кандидатов одновременно проголосовали за себя.

Таймаут выбирается в диапазоне `[600ms, 1200ms)` по умолчанию. Случайность
нужна, чтобы узлы с меньшей вероятностью начинали выборы одновременно и снова
делили голоса. ID узла при выборе победителя не сравнивается.

## 7. Обработка запроса голоса: HandleVote

Функция берёт mutex, проверяет наличие ошибки хранения и принадлежность
кандидата кластеру. Затем вызывает `observeTermLocked`.

Если входящий срок больше текущего, узел становится follower, принимает новый
срок и очищает голос **старого срока**. Новое состояние сохраняется на диск.
Если входящий срок меньше текущего, возвращается отказ с актуальным сроком.

При равных сроках голос даётся при двух условиях. Первое: `VotedFor` пуст или
уже равен тому же кандидату. Повторный запрос от того же кандидата допустим:
это идемпотентность. Запрос от другого кандидата в том же сроке отклоняется.
Второе: журнал кандидата не хуже нашего (см. ниже).

Перед положительным ответом голос сохраняется, затем сбрасывается таймаут
выборов. Отказ в голосе при равном сроке не сбрасывает таймаут. При переходе
в новый срок таймаут в этой реализации переустанавливается самим
`observeTermLocked`.

Журнал кандидата проверяет `candidateLogUpToDateLocked` (§5.4.1). Запрос несёт
`last_log_index` и `last_log_term`. Сравниваются последние записи: журнал с более
поздним сроком последней записи лучше, а при равных сроках лучше более длинный.
Индекс сравнивается только при равных сроках, поэтому короткий журнал с поздним
сроком лучше длинного со старым.

Зачем это нужно: зафиксированная запись есть у большинства, а для избрания нужно
большинство голосов. Эти два большинства пересекаются, поэтому хотя бы один
голосующий имеет запись и откажет кандидату без неё. Так новый лидер всегда
содержит все зафиксированные записи (Leader Completeness).

## 8. Ответы на запросы голосов: requestVote

HTTP-вызов выполняется без mutex. Ошибка сети означает отсутствие голоса,
а не голос против и не доказательство смерти процесса.

После ответа снова берётся mutex. Более высокий срок из ответа всегда
заставляет перейти в follower. Затем проверяется, что узел ещё candidate,
его текущий срок совпадает со сроком отправленного запроса и ответ относится
к тому же сроку.

Это защита от запоздалых ответов: если запрос был отправлен в сроке 2, а узел
уже перешёл в срок 3, старый положительный ответ нельзя считать в новых выборах.

На каждого peer отправляется один запрос на кампанию; ответ учитывается один
раз. После достижения большинства роль уже leader, поэтому дальнейшие ответы
не увеличивают счётчик. Для этой схемы отдельное множество проголосовавших ID
не требуется; при добавлении повторных запросов понадобится защита от повторного
подсчёта голосов.

## 9. Репликация журнала: AppendEntries

### Запись журнала и путь команды

Запись (`Entry`) состоит из индекса, срока и команды. Индексы начинаются с 1.
Индекс и срок вместе однозначно определяют запись. Путь команды клиента:

1. Клиент отправляет `POST /log` лидеру. Другой узел отвечает 409 и подсказывает лидера.
2. `Propose` дописывает записи в журнал лидера и **сохраняет их на диск**.
3. `Propose` обнуляет `nextHeartbeat`, поэтому AppendEntries уходит на ближайшем тике.
4. Follower проверяет журнал, дописывает записи, сохраняет их и отвечает `success`.
5. Лидер обновляет `matchIndex`. Запись у большинства становится зафиксированной.
6. `WaitCommitted` просыпается, и клиент получает ответ 200.
7. Следующий AppendEntries сообщает follower новый `leader_commit`.
8. Каждый узел применяет записи по порядку: `lastApplied` догоняет `commitIndex`.

### Получатель: HandleAppendEntries

Функция выполняет пункты 1–5 из Figure 2:

1. Меньший срок — отказ, таймер выборов не сбрасывается.
2. Нет записи `prev_log_index` со сроком `prev_log_term` — отказ. Лидер законный,
   поэтому таймер выборов всё равно сброшен, а узел признаёт лидера.
3. Конфликт (тот же индекс, другой срок) — запись и всё после неё удаляются.
4. Дописываются записи, которых ещё нет.
5. `commitIndex = min(leader_commit, индекс последней новой записи)`.

В пункте 4 важно не обрезать журнал безусловно. Запросы могут прийти не по
порядку: запоздавший короткий запрос не должен удалить более новые совпадающие
записи. Обрезка происходит только при настоящем конфликте.

В пункте 5 важен именно индекс последней новой записи, а не конец журнала:
за ней журнал follower ещё не сверен с лидером и может содержать чужие записи.
Поэтому после heartbeat с `prev_log_index` = 1 узел не зафиксирует запись 2,
даже если лидер сообщил `leader_commit` = 9. `commitIndex` при этом не уменьшается.

Записи сохраняются на диск **до** ответа `success`: лидер считает узел репликой,
и потеря записи при перезапуске могла бы нарушить большинство.

Heartbeat — это тот же AppendEntries с пустым `entries`, и проверка `prev_log`
для него тоже работает. Голос текущего срока при этом не очищается, иначе можно
было бы проголосовать дважды. Кандидат, получивший AppendEntries от лидера своего
срока, становится follower.

### Лидер: replicateTo

Для каждого peer на каждый heartbeat запускается своя goroutine `replicateTo`,
поэтому медленный узел не задерживает остальных. Из `nextIndex[peer]` строится
запрос: `prev_log_index = nextIndex - 1` и записи начиная с `nextIndex`, не больше
`maxEntriesPerRPC` за раз. Записи копируются, потому что сеть работает без mutex.

- **Успех:** `matchIndex = max(matchIndex, prev + число записей)`, `nextIndex`
  следом. `max` нужен потому, что ответы могут прийти не по порядку. Если ещё
  остались записи, сразу отправляется следующий запрос.
- **Отказ:** журналы разошлись. `nextIndex` уменьшается на 1, и запрос повторяется
  сразу. Так лидер идёт назад до последней совпадающей записи, после чего
  follower удаляет конфликтующие записи и получает записи лидера. Условие
  `nextIndex == prev + 1` не даёт уменьшить индекс дважды из-за двух одинаковых отказов.
- **Больший срок в ответе:** лидер устарел и становится follower.
- **Ошибка сети:** выходим. Повторит следующий heartbeat.

Откат по одной записи — базовый вариант из статьи. Ускоренный откат с подсказкой
от follower статья описывает как необязательную оптимизацию.

### Фиксация: advanceCommitLocked

Лидер ищет наибольший `N > commitIndex`, такой что `N` есть у большинства
(считая самого лидера) и `log[N].term == currentTerm`.

Условие на срок — это §5.4.2 и Figure 8 статьи. Запись **прошлого** срока нельзя
считать зафиксированной только потому, что она у большинства: новый лидер с
более поздним журналом ещё может её перезаписать. Такая запись фиксируется
косвенно, вместе с первой записью текущего срока: по свойству Log Matching
фиксация записи `N` означает фиксацию всех записей до неё.

Следствие: новый лидер не сразу узнаёт, какие записи зафиксированы. Если после
выборов клиенты молчат, `commit_index` не вырастет. В §8 статьи это решается
пустой записью нового лидера, но на Figure 2 её нет, и здесь она не сделана.

### Ответ клиенту

`handleAddEntries` отвечает 200 только после фиксации. Это значит, что запись
уже не потеряется. Остальные варианты:

| Код | Значение |
|---|---|
| 409 | Узел не лидер; в ответе `leader_id` и `leader_address`, если они известны |
| 504 | За 2 секунды запись не зафиксирована. Исход неизвестен: она может быть зафиксирована позже |
| 503 | Запись заменена новым лидером и потеряна, либо ошибка диска |

Проверка в `WaitCommitted` использует пару (индекс, срок). Если на этом индексе
другой срок, наша запись заменена. Простая смена лидера ещё ничего не значит:
новый лидер мог получить запись и зафиксировать её.

Повторная отправка после 504 может продублировать команду: защиты от дублей
(§8 статьи) пока нет. Понадобится вместе с машиной состояний.

## 10. Почему два лидера не могут быть избраны в одном сроке

Для избрания каждому кандидату нужно строгое большинство фиксированного
кластера. Любые два таких большинства пересекаются хотя бы в одном узле.
Если бы два кандидата были избраны в одном сроке, узел из пересечения должен
был бы проголосовать за обоих. Это запрещено правилом `VotedFor` и сохранением
голоса между перезапусками. В статье это свойство называется Election Safety.

Утверждение относится к **одному сроку**. При разделении сети старый лидер
может продолжать локально считать себя лидером в сроке 5, пока большинство
избирает нового в сроке 6. Это не два избранных лидера одного срока.
`GET /status` показывает локальное мнение и не доказывает текущую связь с
большинством. Старый лидер принимает записи, но зафиксировать их не сможет:
большинства у него нет, клиент получит 504, а новый лидер эти записи заменит.

`GET /log` показывает журнал одного узла. Гарантированно одинакова только
зафиксированная часть: незафиксированный хвост может отличаться между узлами
и быть перезаписан. Это ещё не линеаризуемое чтение: узел может отставать.

Свойства безопасности из статьи (Figure 3), которые здесь обеспечиваются:

| Свойство | Чем обеспечено |
|---|---|
| Election Safety | Один голос на срок и большинство |
| Leader Append-Only | Лидер только дописывает в свой журнал |
| Log Matching | Проверка `prev_log_index`/`prev_log_term` в AppendEntries |
| Leader Completeness | Проверка журнала при голосовании и правило фиксации текущего срока |
| State Machine Safety | Применение только зафиксированных записей строго по порядку |

## 11. Параллельность в Go

`go func(...)` запускает goroutine: лёгкую задачу, которой управляет runtime Go.
Запросы к peers идут параллельно, чтобы один медленный сервер не задерживал
обращения к остальным.

HTTP-сервер также обрабатывает запросы конкурентно. Одновременно могут работать
таймер выборов, входящий запрос голоса, AppendEntries и `/status`. Поэтому изменяемые
поля защищены `sync.Mutex`. Без него возможна не только гонка данных, но и
ошибка протокола: два обработчика могут одновременно увидеть пустой `VotedFor`
и выдать голоса разным кандидатам.

Суффикс `Locked` означает: вызывающая функция уже должна держать mutex.
Дисковая запись остаётся под mutex, чтобы никто не подтвердил голос или запись
до их сохранения. Весь `state.json` перезаписывается при каждом изменении журнала,
поэтому запись становится дороже с ростом журнала. Для учебного проекта это
просто; для высокой нагрузки понадобится журнал с дозаписью в конец файла.

Сетевой запрос выполняется **после освобождения mutex**. Затем состояние
проверяется заново: за время ожидания роль или срок могли измениться.
`Status` и `Log` возвращают копии, чтобы вызывающий код не получил доступ к
внутренним изменяемым структурам. По той же причине записи для AppendEntries
копируются до снятия mutex: иначе обрезка журнала и кодирование JSON в другой
goroutine работали бы с одним массивом.

Клиентский запрос ждёт фиксации на канале `changed`. `notifyLocked` закрывает его
и создаёт новый: закрытие канала будит всех ожидающих сразу. После пробуждения
`WaitCommitted` заново проверяет запись под mutex. В отличие от `sync.Cond`,
канал можно ждать в `select` вместе с таймаутом контекста.

`time.Ticker` — периодический источник событий. Пример:

```go
ticker := time.NewTicker(10 * time.Millisecond)
defer ticker.Stop()
```

Примерно каждые 10 ms тикер передаёт время в канал `ticker.C`. Основной цикл
ждёт либо это событие, либо отмену через `ctx.Done()`. В ожидании событий
не происходит непрерывного опроса, который тратил бы процессор впустую.
При медленной обработке тики могут пропускаться: это не жёсткие часы реального времени.

Тик — повод проверить таймеры, а не команда немедленно проводить выборы.
Например, при таймауте выборов 800 ms тики на 10, 20 и 30 ms сами по себе
ничего не меняют. Выборы начнутся, когда проверка обнаружит истёкший `deadline`,
если до этого актуальный heartbeat не перенесёт его. Heartbeat отправляется
по собственному расписанию, по умолчанию раз в 100 ms.

Основной цикл оставлен коротким, а действия распределены по методам:

| Метод | Ответственность |
|---|---|
| `Run` | Ждать тик или отмену; при остановке дождаться исходящих задач |
| `handleTick` | Проверить состояние и решить, пора ли начать выборы или отправить AppendEntries |
| `startElectionLocked` | Подготовить и сохранить новую кампанию под mutex |
| `broadcastVoteRequests` | Запустить отдельный запрос голоса каждому peer |
| `broadcastAppendEntries` | Запустить отдельную goroutine `replicateTo` каждому peer |
| `requestVote` | Получить ответ одного peer и учесть голос, если кампания ещё актуальна |
| `replicateTo` | Довести журнал одного peer до журнала лидера |
| `handleAppendEntriesResponseLocked` | Обновить `nextIndex`/`matchIndex` или уступить при большем сроке |
| `advanceCommitLocked` | Найти новую зафиксированную запись по `matchIndex` |

`context.Context` передаёт отмену запросам при остановке.
`sync.WaitGroup` позволяет дождаться завершения исходящих goroutine.
Задачи добавляются из методов рассылки, вызванных основным циклом. При выходе
цикл прекращает их добавление, отменяет контекст и ждёт оставшиеся задачи.
Это ожидание завершения при остановке, а не ожидание всех голосов в каждом раунде.

## 12. HTTP и REST

`HTTPTransport.call` сериализует структуру в JSON, создаёт POST-запрос,
отправляет его через `http.Client` и декодирует ответ. JSON-теги вроде
`json:"candidate_id"` задают имена полей в сети. Клиент ограничивает время RPC,
а контекст позволяет отменить его раньше.

`Handler` создаёт `http.ServeMux`. Шаблоны `GET /status` и
`POST /raft/request-vote` одновременно задают путь и разрешённый метод.
Входящий JSON ограничен 1 MiB, неизвестные поля и лишний JSON после первого
объекта отвергаются. Команда ограничена 4 KiB: иначе одна запись могла бы не
поместиться в AppendEntries, и репликация застряла бы навсегда.
Внутренние маршруты — это RPC поверх HTTP/JSON; `GET /status`, `GET /log`
и `POST /log` — пользовательский REST API.

## 13. Сохранение состояния

`Storage` — интерфейс с `Load` и `Save`. Ядро зависит от поведения хранилища,
а не от конкретного файла. В тестах можно использовать память или искусственную
ошибку диска; в приложении используется `FileStorage`.

`state.json` содержит примерно следующее:

```json
{"term":3,"voted_for":"n2","log":[{"index":1,"term":1,"command":"set a=1"}]}
```

`Save` создаёт временный файл в том же каталоге, пишет JSON, вызывает `Sync`,
закрывает файл и переименовывает его в `state.json`. Это уменьшает риск получить
частично записанный JSON и поддерживает обычные остановки и перезапуски процесса.
Переименование и устойчивость при отключении питания зависят от ОС и файловой
системы; здесь нет полноценного промышленного transactional storage и синхронизации
каталога. Особенно на Windows нельзя обещать универсальную атомарность `Rename`.

Если запись не удалась, узел не подтверждает голос или записи и прекращает
участие. Продолжать после ошибки было бы опасно: при перезапуске узел мог забыть
выданный голос или запись, которую лидер уже посчитал реплицированной. Данные нельзя
удалять между перезапусками в том же кластере и нельзя делить каталог между процессами.

## 14. Точка входа и остановка

`main.go` разбирает флаги через пакет `flag`. `parsePeers` проверяет формат
`id=http://host:port`, запрещает собственный ID и дубли peers. Далее создаются
клиент, хранилище и узел.

Сначала выполняется `net.Listen`, и только затем запускаются сервер и `Run`.
Если порт занят, процесс завершится до начала выборов. Это исключает ситуацию,
когда недоступный по своему порту процесс уже объявляет себя лидером.

Сервер и цикл узла отправляют результат в канал `results`. При Ctrl+C,
ошибке сервера или ошибке ядра отменяется контекст, HTTP-сервер корректно
останавливается и программа ждёт завершения обеих частей. Отдельный контекст
для shutdown имеет срок 3 секунды; при превышении сервер закрывается принудительно.

## 15. Что проверяют тесты

Тесты проверяют конкретные свойства, а не только успешную сборку:

- Один голос на срок, включая повторный запуск с тем же файлом состояния.
- Повторный голос за того же кандидата и возможность голосовать в новом сроке.
- Конкурентные запросы двух кандидатов: голоса получает только один ID.
- Отказ старым сообщениям и переход в follower при актуальном heartbeat.
- Сохранение голоса при heartbeat того же срока.
- Прекращение участия после ошибки хранилища.
- Запоздалые ответы и больший срок из ответа RPC.
- HTTP-обмен, отказ неизвестному участнику, некорректный метод и пустой JSON.
- Повторные выборы без ответов peers.
- Выбор единственного лидера и стабильность срока при heartbeat через настоящие HTTP-серверы.
- Перевыборы после остановки лидера; невозможность избрания оставшегося follower без большинства.
- Самоизбрание кластера из одного узла.
- Голос только кандидату с журналом не хуже нашего; отказ не сбрасывает таймер выборов.
- Больший срок не стирает журнал.
- Все пункты получателя AppendEntries: проверка `prev_log`, удаление при конфликте,
  запоздавший запрос не обрезает журнал, ограничение `commitIndex`, журнал после перезапуска.
- Запрет перезаписи зафиксированной записи и отказ на некорректные запросы.
- Фиксация только записей текущего срока (Figure 8).
- Лидер чинит разошедшийся журнал follower; отставший узел догоняет порциями.
- Ответы не по порядку не откатывают `matchIndex` и не уменьшают `nextIndex` дважды.
- Клиент узнаёт о записи, заменённой новым лидером.
- Кластер: записи доходят до всех, новый лидер имеет зафиксированные записи и продолжает журнал.
- Без большинства запись не фиксируется.
- REST: `POST /log`, `GET /log`, ошибки 400 и 409 с адресом лидера.

Интеграционные тесты запускают реальные локальные HTTP-серверы в одном процессе.
Это проверяет таймеры и транспорт, но не является формальным доказательством
корректности и не заменяет испытания всех возможных сетевых разделений.

## 16. Короткий рассказ на защите

«Я реализовал выборы лидера и репликацию журнала Raft по Figure 2 статьи.
Каждый узел запускается отдельным Go-процессом и имеет роли follower, candidate и leader.
При отсутствии heartbeat узел ждёт случайный таймаут, увеличивает срок,
голосует за себя и запрашивает голоса остальных. Для победы нужно строгое
большинство фиксированного состава кластера. В одном сроке каждый узел голосует
только за одного кандидата; срок и голос сохраняются на диск. Лидер отправляет
heartbeat, а обнаружение большего срока переводит узел обратно в follower.
REST endpoint `/status` показывает локальную роль, срок и известного лидера.

Клиент отправляет команду лидеру через `POST /log`. Лидер дописывает её в свой
журнал, сохраняет на диск и рассылает через AppendEntries. Follower проверяет по
`prev_log_index` и `prev_log_term`, что журналы совпадают, а при расхождении лидер
откатывает `nextIndex` и исправляет журнал follower. Когда запись текущего срока
есть у большинства, лидер её фиксирует и отвечает клиенту. Голос даётся только
кандидату с журналом не хуже своего, поэтому новый лидер имеет все зафиксированные
записи. `GET /log` показывает журнал узла. Машина состояний — следующий этап».

## 17. Частые вопросы

**Почему нельзя просто выбрать максимальный ID?** Это был бы другой алгоритм,
близкий к слайдам. Задание развивается в Raft, где согласование лидерства
осуществляется большинством голосов в сроке.

**Почему нужны случайные таймауты?** Чтобы уменьшить вероятность одновременного
начала кампаний и повторного разделения голосов.

**Почему срок хранится на диске?** Чтобы после перезапуска не принимать
устаревшие сообщения как новые. Голос хранится, чтобы не голосовать повторно
за другого кандидата в том же сроке.

**Почему после остановки двух серверов кластер не уменьшается до одного?**
Состав кластера фиксирован. Автоматически считать недоступных исключёнными
опасно: две части сети могли бы каждая назначить себе большинство.

**Гарантируется ли выбор лидера при любой сети?** Нет. Без доступного большинства
или при постоянных больших задержках прогресс не гарантируется.

**Почему старый лидер при изоляции не всегда становится follower?** В базовых
правилах он уступает при обнаружении большего срока. В этой версии нет
дополнительного check-quorum, который заставлял бы уступать при длительной
потере связи с большинством. Статус отражает локальное состояние.

**Чем heartbeat отличается от репликации?** Ничем, кроме пустого `entries`.
Это один и тот же RPC с той же проверкой журнала.

**Запись есть у большинства. Она зафиксирована?** Если она из текущего срока, то
да. Если из прошлого — нет, пока не зафиксирована запись текущего срока (Figure 8).

**Может ли follower удалить запись?** Да, но только незафиксированную. Зафиксированные
записи не удаляются: новый лидер их содержит, поэтому конфликта с ними быть не может.

**Почему `commitIndex` не сохраняется на диск?** Он восстанавливается от лидера.
Figure 2 относит его к изменчивому состоянию. После перезапуска записи применяются заново.

**Зачем и `nextIndex`, и `matchIndex`?** `nextIndex` — оптимистичное предположение,
откуда отправлять, оно может быть неверным и уменьшается при отказе. `matchIndex` —
подтверждённое знание, только растёт и используется для фиксации.

**Почему лидер не дожидается всех узлов?** Достаточно большинства: так недоступное
меньшинство не останавливает кластер. Отставший узел догонит лидера позже.

**Что будет с записью, если лидер упал до фиксации?** Если она попала к новому
лидеру, она сохранится и зафиксируется позже. Если нет — будет заменена. Клиент
в этом случае не получал ответа 200, поэтому обещание не нарушено.

**Что нужно добавить дальше?** Машину состояний key-value, применение записей
к ней, CAS, распределённую блокировку и защиту от повторного выполнения команд.
