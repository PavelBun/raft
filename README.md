# Raft на Go — этапы 1 и 2

Учебная реализация Raft по [оригинальной статье](https://raft.github.io/raft.pdf)
(Figure 2): каркас узла, выборы лидера, репликация журнала, машина состояний
key-value в памяти и REST API для статуса, добавления записей и просмотра журнала.
CAS и распределённая блокировка пока не реализованы.

Всё состояние узла хранится в памяти: срок, голос, журнал и данные key-value.
Перезапущенный узел начинает с пустого состояния и догоняет журнал от лидера.

Требуется Go 1.25 или новее. Внешних Go-зависимостей нет.

## Быстрый запуск на Windows

В PowerShell из папки проекта:

```powershell
go build -o bin/raft.exe ./cmd/raft
```

Открой три терминала в этой папке. В каждом запусти одну команду.

Первый терминал:

```powershell
.\bin\raft.exe -id n1 -listen 127.0.0.1:8001 -peers "n2=http://127.0.0.1:8002,n3=http://127.0.0.1:8003"
```

Второй терминал:

```powershell
.\bin\raft.exe -id n2 -listen 127.0.0.1:8002 -peers "n1=http://127.0.0.1:8001,n3=http://127.0.0.1:8003"
```

Третий терминал:

```powershell
.\bin\raft.exe -id n3 -listen 127.0.0.1:8003 -peers "n1=http://127.0.0.1:8001,n2=http://127.0.0.1:8002"
```

В четвёртом терминале запроси состояние:

```powershell
8001..8003 | ForEach-Object {
    Invoke-RestMethod "http://127.0.0.1:$_/status"
} | Format-Table id,role,term,leader_id,voted_for,last_log_index,commit_index,last_applied
```

После стабилизации один узел будет `leader`, два — `follower`. Все живые узлы
должны указать одного лидера. Номер срока и ID лидера заранее не фиксированы.

## Команды key-value

Машина состояний понимает три команды:

| Команда | Результат |
|---|---|
| `set <ключ> <значение>` | Записывает значение; `found: true` и новое значение |
| `get <ключ>` | Значение и `found`: есть ли ключ |
| `delete <ключ>` | Удаляет ключ; `found`: был ли он |

Ключ без пробелов, значение может содержать пробелы. Команды отправляются лидеру
через журнал: и запись, и чтение проходят через Raft, поэтому `get` возвращает
значение с учётом всех предыдущих команд.

Подставь порт лидера вместо `8001`. Одна команда:

```powershell
(Invoke-RestMethod -Method Post "http://127.0.0.1:8001/log" -ContentType "application/json" -Body '{"command":"set a 1"}').results
```

Несколько команд одним запросом:

```powershell
(Invoke-RestMethod -Method Post "http://127.0.0.1:8001/log" -ContentType "application/json" -Body '{"commands":["set b 2","get a","delete a"]}').results
```

Журналы всех трёх узлов:

```powershell
8001..8003 | ForEach-Object {
    $log = Invoke-RestMethod "http://127.0.0.1:$_/log"
    $log.entries | Select-Object @{n='node';e={$log.id}},index,term,command,committed
} | Format-Table
```

Данные key-value всех трёх узлов:

```powershell
8001..8003 | ForEach-Object { Invoke-RestMethod "http://127.0.0.1:$_/kv" } | Format-Table id,last_applied,data
```

Ответ приходит после того, как запись зафиксирована у большинства и выполнена
машиной состояний. Если отправить команду не лидеру, он ответит 409 и подскажет
адрес лидера. В Windows PowerShell такой ответ выглядит как красная ошибка
с этим JSON внутри. Пиши команды латиницей: Windows PowerShell 5.1 портит
кириллицу в теле запроса.

## Запуск пяти узлов

Отдельный эксперимент: кластер из пяти узлов на портах 8011–8015. Он не
пересекается с кластером из трёх узлов выше. Открой пять терминалов и в каждом
запусти одну команду.

Первый терминал:

```powershell
.\bin\raft.exe -id n1 -listen 127.0.0.1:8011 -peers "n2=http://127.0.0.1:8012,n3=http://127.0.0.1:8013,n4=http://127.0.0.1:8014,n5=http://127.0.0.1:8015"
```

Второй терминал:

```powershell
.\bin\raft.exe -id n2 -listen 127.0.0.1:8012 -peers "n1=http://127.0.0.1:8011,n3=http://127.0.0.1:8013,n4=http://127.0.0.1:8014,n5=http://127.0.0.1:8015"
```

Третий терминал:

```powershell
.\bin\raft.exe -id n3 -listen 127.0.0.1:8013 -peers "n1=http://127.0.0.1:8011,n2=http://127.0.0.1:8012,n4=http://127.0.0.1:8014,n5=http://127.0.0.1:8015"
```

Четвёртый терминал:

```powershell
.\bin\raft.exe -id n4 -listen 127.0.0.1:8014 -peers "n1=http://127.0.0.1:8011,n2=http://127.0.0.1:8012,n3=http://127.0.0.1:8013,n5=http://127.0.0.1:8015"
```

Пятый терминал:

```powershell
.\bin\raft.exe -id n5 -listen 127.0.0.1:8015 -peers "n1=http://127.0.0.1:8011,n2=http://127.0.0.1:8012,n3=http://127.0.0.1:8013,n4=http://127.0.0.1:8014"
```

Статус всех пяти узлов:

```powershell
8011..8015 | ForEach-Object {
    Invoke-RestMethod "http://127.0.0.1:$_/status"
} | Format-Table id,role,term,leader_id,voted_for,last_log_index,commit_index,last_applied
```

Для пяти узлов `majority` равно 3: кластер переживает отказ любых двух узлов.
Если остановить лидера и ещё один узел, оставшиеся три выберут нового лидера.
Если остановить три узла, двух оставшихся голосов для выборов не хватит.

Для Linux/macOS собери `go build -o bin/raft ./cmd/raft`, затем запускай
`./bin/raft` с такими же параметрами; для статуса используй `curl localhost:8001/status`.

## Демонстрация преподавателю

1. Запусти три узла и покажи статусы. Большинство для трёх узлов — два голоса.
2. Отправь лидеру `set a 1`, `set b 2`, `get a`: в ответе результаты команд. Покажи журналы и `/kv` всех узлов: они одинаковы.
3. Отправь команду follower: он откажет и назовёт лидера.
4. Останови follower через Ctrl+C и отправь `set c 3`: команда выполнится, потому что большинство живо.
5. Запусти этот follower той же командой. Он стартует с пустой памятью. Лидер получает отказы, со следующими heartbeat уменьшает `next_index` до совпадения и дошлёт весь журнал. После этого `/kv` у follower совпадает с остальными.
6. Останови лидера. Подожди примерно 1–3 секунды и опроси **два оставшихся** адреса. Они выберут нового лидера в большем сроке, и данные останутся. Это ориентир для локального запуска, а не гарантия времени.
7. Отправь `get c` новому лидеру: вернётся `3`. Запусти старого лидера: он станет follower и догонит журнал.
8. Останови два узла. Если остался follower, он будет пытаться провести выборы, но одного голоса недостаточно. Если остался leader, его команда получит ответ 504: большинства нет, запись остаётся `committed: False`. Его роль может оставаться `leader`, потому что check-quorum здесь нет.

У каждого узла должны быть отдельные ID и порт. Все узлы должны иметь одинаковый
фиксированный состав кластера. `-peers` содержит всех остальных, а не только сейчас
доступные узлы. Для нового чистого эксперимента достаточно перезапустить все узлы.

## REST API

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/status` | Локальное состояние узла |
| POST | `/log` | Добавить команды; только лидер, ответ после выполнения |
| GET | `/log` | Журнал этого узла |
| GET | `/kv` | Данные машины состояний этого узла |
| POST | `/raft/request-vote` | Внутренний RPC запроса голоса |
| POST | `/raft/append-entries` | Внутренний RPC: репликация записей и heartbeat |

Пример `GET /status` для лидера:

```json
{
  "id": "n2",
  "role": "leader",
  "term": 1,
  "leader_id": "n2",
  "voted_for": "n2",
  "votes": 2,
  "cluster_size": 3,
  "majority": 2,
  "last_log_index": 3,
  "last_log_term": 1,
  "commit_index": 3,
  "last_applied": 3,
  "next_index": { "n1": 4, "n3": 4 },
  "match_index": { "n1": 3, "n3": 3 },
  "peers": {
    "n1": "http://127.0.0.1:8001",
    "n3": "http://127.0.0.1:8003"
  }
}
```

`leader_id` — известный этому узлу лидер; пустая строка означает, что он неизвестен.
`votes` — счётчик текущей собственной кампании; у follower он обычно равен нулю.
Лидер прекращает считать голоса после достижения большинства, поэтому `votes`
может быть 2, даже когда фактически все три узла проголосовали за него.
Это не счётчик доступных серверов. `voted_for` относится к текущему сроку и может
отличаться от `leader_id`: кандидат может проиграть выборы другому кандидату.
`commit_index` — последняя запись, про которую узел знает, что она зафиксирована,
`last_applied` — последняя выполненная машиной состояний. `next_index` и
`match_index` есть только у лидера.

`POST /log` принимает `{"command":"set a 1"}` или `{"commands":["set a 1","get a"]}`:
до 100 команд до 4 КиБ каждая. Успешный ответ содержит результат каждой команды:

```json
{"results":[{"index":1,"term":1,"value":"1","found":true},{"index":2,"term":1,"value":"1","found":true}]}
```

| Код `POST /log` | Значение |
|---|---|
| 200 | Команды зафиксированы и выполнены; в ответе результаты |
| 400 | Некорректный запрос или неизвестная команда |
| 409 | Узел не лидер; в ответе `leader_id` и `leader_address`, если лидер известен |
| 503 | Запись заменена новым лидером, команда не выполнена |
| 504 | За 2 секунды команда не выполнена, например нет большинства. Она может выполниться позже |

`GET /log` возвращает журнал с отметкой о фиксации:

```json
{
  "id": "n1",
  "role": "follower",
  "term": 1,
  "leader_id": "n2",
  "commit_index": 1,
  "last_applied": 1,
  "entries": [
    { "index": 1, "term": 1, "command": "set a 1", "committed": true }
  ]
}
```

`GET /kv` возвращает данные машины состояний узла:
`{"id":"n1","last_applied":3,"data":{"a":"1","b":"2"}}`.

Внутренние RPC совпадают с Figure 2 статьи. Запрос голоса:
`{"term":2,"candidate_id":"n2","last_log_index":3,"last_log_term":1}`, ответ —
`{"term":2,"vote_granted":true}`. AppendEntries:
`{"term":2,"leader_id":"n2","prev_log_index":3,"prev_log_term":1,"entries":[...],"leader_commit":3}`,
ответ — `{"term":2,"success":true}`. Пустой `entries` — это heartbeat. При отказе
follower добавляет подсказку для ускоренного отката (§5.3):
`{"term":2,"success":false,"conflict_term":1,"conflict_index":4}`.

Для внутренних RPC HTTP 200 означает, что запрос обработан: голос при этом может
быть отклонён. Ошибки JSON, неизвестный ID и некорректные поля дают 400; попытка
перезаписать зафиксированную запись — 409; неправильный HTTP-метод — 405.
API предназначен для доверенного учебного кластера; проверки ID не являются аутентификацией.

## Параметры и проверки

| Флаг | По умолчанию | Значение |
|---|---|---|
| `-id` | требуется | Уникальный ID |
| `-listen` | `127.0.0.1:8001` | Адрес HTTP-сервера |
| `-peers` | пусто | Остальные узлы; пустой список создаёт кластер из одного узла |
| `-heartbeat` | `100ms` | Интервал heartbeat |
| `-election-min` | `600ms` | Нижняя граница таймаута выборов |
| `-election-max` | `1200ms` | Верхняя граница таймаута, не включается |
| `-rpc-timeout` | `250ms` | Предельная длительность HTTP-запроса |

```powershell
go test ./...
go vet ./...
```

`go test -race ./...`. В исходном Windows-окружении CGO отключён и C-компилятор
не найден, поэтому race detector здесь не запускался.
