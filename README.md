# Raft на Go — этапы 1 и 2

Учебная реализация Raft по [оригинальной статье](https://raft.github.io/raft.pdf)
(Figure 2): каркас узла, выборы лидера, репликация журнала и REST API для статуса,
добавления записей и просмотра журнала.
Key-value, CAS и распределённая блокировка пока не реализованы.

Требуется Go 1.25 или новее. Внешних Go-зависимостей нет.

## Быстрый запуск на Windows

В PowerShell из папки проекта:

```powershell
go build -o bin/raft.exe ./cmd/raft
```

Открой три терминала в этой папке. В каждом запусти одну команду.

Первый терминал:

```powershell
.\bin\raft.exe -id n1 -listen 127.0.0.1:8001 -peers "n2=http://127.0.0.1:8002,n3=http://127.0.0.1:8003" -data data/n1
```

Второй терминал:

```powershell
.\bin\raft.exe -id n2 -listen 127.0.0.1:8002 -peers "n1=http://127.0.0.1:8001,n3=http://127.0.0.1:8003" -data data/n2
```

Третий терминал:

```powershell
.\bin\raft.exe -id n3 -listen 127.0.0.1:8003 -peers "n1=http://127.0.0.1:8001,n2=http://127.0.0.1:8002" -data data/n3
```

В четвёртом терминале запроси состояние:

```powershell
8001..8003 | ForEach-Object {
    Invoke-RestMethod "http://127.0.0.1:$_/status"
} | Format-Table id,role,term,leader_id,voted_for,last_log_index,commit_index,last_applied
```

После стабилизации один узел будет `leader`, два — `follower`. Все живые узлы
должны указать одного лидера. Номер срока и ID лидера заранее не фиксированы.

## Добавить записи и посмотреть журнал

Записи принимает только лидер. Подставь его порт вместо `8001`. Одна запись:

```powershell
Invoke-RestMethod -Method Post "http://127.0.0.1:8001/log" -ContentType "application/json" -Body '{"command":"set a=1"}'
```

Несколько записей одним запросом:

```powershell
Invoke-RestMethod -Method Post "http://127.0.0.1:8001/log" -ContentType "application/json" -Body '{"commands":["set b=2","set c=3"]}'
```

Журнал одного узла:

```powershell
(Invoke-RestMethod "http://127.0.0.1:8001/log").entries | Format-Table index,term,command,committed
```

Журналы всех трёх узлов:

```powershell
8001..8003 | ForEach-Object {
    $log = Invoke-RestMethod "http://127.0.0.1:$_/log"
    $log.entries | Select-Object @{n='node';e={$log.id}},index,term,command,committed
} | Format-Table
```

Ответ приходит после фиксации записи, то есть когда она есть у большинства.
Если отправить запись не лидеру, он ответит 409 и подскажет адрес лидера. В
Windows PowerShell такой ответ выглядит как красная ошибка с этим JSON внутри.

## Запуск пяти узлов

Отдельный эксперимент: кластер из пяти узлов на портах 8011–8015, со своими
каталогами `data/five-n1` … `data/five-n5`. Он не пересекается с кластером из
трёх узлов выше. Открой пять терминалов и в каждом запусти одну команду.

Первый терминал:

```powershell
.\bin\raft.exe -id n1 -listen 127.0.0.1:8011 -peers "n2=http://127.0.0.1:8012,n3=http://127.0.0.1:8013,n4=http://127.0.0.1:8014,n5=http://127.0.0.1:8015" -data data/five-n1
```

Второй терминал:

```powershell
.\bin\raft.exe -id n2 -listen 127.0.0.1:8012 -peers "n1=http://127.0.0.1:8011,n3=http://127.0.0.1:8013,n4=http://127.0.0.1:8014,n5=http://127.0.0.1:8015" -data data/five-n2
```

Третий терминал:

```powershell
.\bin\raft.exe -id n3 -listen 127.0.0.1:8013 -peers "n1=http://127.0.0.1:8011,n2=http://127.0.0.1:8012,n4=http://127.0.0.1:8014,n5=http://127.0.0.1:8015" -data data/five-n3
```

Четвёртый терминал:

```powershell
.\bin\raft.exe -id n4 -listen 127.0.0.1:8014 -peers "n1=http://127.0.0.1:8011,n2=http://127.0.0.1:8012,n3=http://127.0.0.1:8013,n5=http://127.0.0.1:8015" -data data/five-n4
```

Пятый терминал:

```powershell
.\bin\raft.exe -id n5 -listen 127.0.0.1:8015 -peers "n1=http://127.0.0.1:8011,n2=http://127.0.0.1:8012,n3=http://127.0.0.1:8013,n4=http://127.0.0.1:8014" -data data/five-n5
```

Статус всех пяти узлов:

```powershell
8011..8015 | ForEach-Object {
    Invoke-RestMethod "http://127.0.0.1:$_/status"
} | Format-Table id,role,term,leader_id,voted_for,last_log_index,commit_index,last_applied
```

Для пяти узлов `majority` равно 3: кластер переживает отказ любых двух узлов.
Если остановить лидера и ещё один узел, оставшиеся три выберут нового лидера.
Если остановить три узла, двух оставшихся голосов для выборов не хватит.

Для Linux/macOS собери `go build -o bin/raft ./cmd/raft`, затем запускай
`./bin/raft` с такими же параметрами; для статуса используй `curl localhost:8001/status`.

## Демонстрация преподавателю

1. Запусти три узла и покажи статусы. Большинство для трёх узлов — два голоса.
2. Добавь записи на лидере и покажи журналы всех узлов: они одинаковы, `committed` равно `True`.
3. Отправь запись follower: он откажет и назовёт лидера.
4. Останови follower через Ctrl+C и добавь запись: она зафиксируется, потому что большинство живо.
5. Запусти этот follower той же командой, с тем же `-data`. Он загрузит журнал с диска, а недостающую запись получит от лидера.
6. Останови лидера. Подожди примерно 1–3 секунды и опроси **два оставшихся** адреса. Они выберут нового лидера в большем сроке, и все записи останутся. Это ориентир для локального запуска, а не гарантия времени.
7. Добавь запись на новом лидере и запусти старого лидера. Он станет follower и догонит журнал.
8. Останови два узла. Если остался follower, он будет пытаться провести выборы, но одного голоса недостаточно. Если остался leader, его запись получит ответ 504 и останется `committed: False`: большинства нет. Его роль может оставаться `leader`, потому что check-quorum здесь нет.

У каждого узла должны быть отдельные ID, порт и каталог данных. Все узлы должны
иметь одинаковый фиксированный состав кластера. `-peers` содержит всех остальных,
а не только сейчас доступные узлы. Не удаляй `state.json` у узла работающего
кластера: это уничтожает память о голосе и журнал. Один каталог нельзя одновременно
использовать в двух процессах. Для нового чистого эксперимента можно остановить весь
кластер и выбрать новые каталоги данных для всех узлов.

## REST API

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/status` | Локальное состояние узла |
| POST | `/raft/request-vote` | Внутренний RPC запроса голоса |
| POST | `/log` | Добавить записи; только лидер, ответ после фиксации |
| GET | `/log` | Журнал этого узла |
| POST | `/raft/append-entries` | Внутренний RPC: репликация записей и heartbeat |

Пример `GET /status` для лидера:

```json
{
  "id": "n2",
  "role": "leader",
  "term": 1,
  "leader_id": "n2",
  "voted_for": "n2",
  "votes": 2,
  "cluster_size": 3,
  "majority": 2,
  "last_log_index": 3,
  "last_log_term": 1,
  "commit_index": 3,
  "last_applied": 3,
  "next_index": { "n1": 4, "n3": 4 },
  "match_index": { "n1": 3, "n3": 3 },
  "peers": {
    "n1": "http://127.0.0.1:8001",
    "n3": "http://127.0.0.1:8003"
  }
}
```

`leader_id` — известный этому узлу лидер; пустая строка означает, что он неизвестен.
`votes` — счётчик текущей собственной кампании; у follower он обычно равен нулю.
Лидер прекращает считать голоса после достижения большинства, поэтому `votes`
может быть 2, даже когда фактически все три узла проголосовали за него.
Это не счётчик доступных серверов. `voted_for` относится к текущему сроку и может
отличаться от `leader_id`: кандидат может проиграть выборы другому кандидату.
`commit_index` — последняя запись, про которую узел знает, что она зафиксирована,
`last_applied` — последняя применённая. `next_index` и `match_index` есть только у лидера.
Машины состояний пока нет: применённая запись только пишется в лог процесса.

`POST /log` принимает `{"command":"x"}` или `{"commands":["x","y"]}`: до 100 непустых
команд до 4 КиБ каждая. Успешный ответ — `{"committed":true,"first_index":1,"last_index":2,"term":1}`.

| Код `POST /log` | Значение |
|---|---|
| 200 | Записи зафиксированы |
| 400 | Некорректный запрос |
| 409 | Узел не лидер; в ответе `leader_id` и `leader_address`, если лидер известен |
| 503 | Запись заменена новым лидером, либо ошибка диска |
| 504 | За 2 секунды нет фиксации, например нет большинства. Запись может быть зафиксирована позже |

`GET /log` возвращает журнал с отметкой о фиксации:

```json
{
  "id": "n1",
  "role": "follower",
  "term": 1,
  "leader_id": "n2",
  "commit_index": 1,
  "last_applied": 1,
  "entries": [
    { "index": 1, "term": 1, "command": "set a=1", "committed": true }
  ]
}
```

Внутренние RPC совпадают с Figure 2 статьи. Запрос голоса:
`{"term":2,"candidate_id":"n2","last_log_index":3,"last_log_term":1}`, ответ —
`{"term":2,"vote_granted":true}`. AppendEntries:
`{"term":2,"leader_id":"n2","prev_log_index":3,"prev_log_term":1,"entries":[...],"leader_commit":3}`,
ответ — `{"term":2,"success":true}`. Пустой `entries` — это heartbeat.

Для внутренних RPC HTTP 200 означает, что запрос обработан: голос при этом может
быть отклонён. Ошибки JSON, неизвестный ID и некорректные поля дают 400; неправильный
HTTP-метод — 405. Ошибка сохранения состояния даёт 503, узел прекращает участвовать в протоколе
и процесс завершается с ошибкой. API предназначен для доверенного учебного
кластера; проверки ID не являются аутентификацией.

## Параметры и проверки

| Флаг | По умолчанию | Значение |
|---|---|---|
| `-id` | требуется | Уникальный ID |
| `-listen` | `127.0.0.1:8001` | Адрес HTTP-сервера |
| `-peers` | пусто | Остальные узлы; пустой список создаёт кластер из одного узла |
| `-data` | требуется | Каталог `state.json`: срок, голос и журнал |
| `-heartbeat` | `100ms` | Интервал heartbeat |
| `-election-min` | `600ms` | Нижняя граница таймаута выборов |
| `-election-max` | `1200ms` | Верхняя граница таймаута, не включается |
| `-rpc-timeout` | `250ms` | Предельная длительность HTTP-запроса |

```powershell
go test ./...
go vet ./...
```
